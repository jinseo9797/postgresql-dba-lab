# PostgreSQL JOIN 성능 최적화 실험

## 1. 실험 목적 및 환경

PostgreSQL 16의 이커머스 합성 데이터에서 특정 고객의 주문별 금액을 조회하는 JOIN 쿼리를 분석했습니다. `EXPLAIN (ANALYZE, BUFFERS)`로 테이블 접근 방식, 실행 시간 및 버퍼 사용량을 비교했습니다.

| 테이블 | 데이터 수 |
|---|---:|
| 고객 | 10,000건 |
| 상품 | 1,000건 |
| 주문 | 100,000건 |
| 주문상세 | 200,000건 |

## 2. 문제 확인

인덱스 적용 전에는 `orders`에서 Seq Scan, `order_items`에서 Parallel Seq Scan이 발생했습니다. 고객 500번의 주문 10건과 관련 주문상세 20건을 조회하는 과정에서 대량의 데이터를 검사했습니다.

## 3. 개선 내용

검색 조건과 JOIN 키를 기준으로 아래 인덱스를 설계했습니다.

```sql
-- 고객 검색과 최신 주문 순 조회를 고려한 복합 인덱스
CREATE INDEX idx_orders_customer_date
ON ecommerce_bench.orders (customer_id, ordered_at DESC);

-- 주문 ID를 기준으로 상세 데이터를 탐색하는 인덱스
CREATE INDEX idx_order_items_order_id
ON ecommerce_bench.order_items (order_id);
```

인덱스 적용 후 `orders`에는 Bitmap Index Scan과 Bitmap Heap Scan이, `order_items`에는 Index Scan이 선택되었습니다. JOIN은 Nested Loop 중심으로 변경되었습니다.

## 4. 측정 결과

| 측정 조건 | Execution Time |
|---|---:|
| 인덱스 적용 전 단회 | 17.621 ms |
| 인덱스 적용 직후 단회 | 1.111 ms |
| 인덱스 사용 5회 평균(1차) | 0.2244 ms |
| 인덱스 사용 5회 평균(2차) | 0.1818 ms |
| 인덱스 스캔 제한 5회 평균(최종) | 18.9172 ms |

- 적용 전 최상위 버퍼: `shared hit=2442`
- 적용 직후 최상위 버퍼: `shared hit=53 read=13`
- 단회 실행 시간 비교: 17.621ms → 1.111ms (약 93.7% 감소)
- 인덱스 사용 2차 평균과 스캔 제한 최종 평균의 비율은 약 104배입니다. 이 수치를 보조 인덱스 두 개만의 독립적인 개선 효과로 해석하지 않았습니다.

## 5. 해석 및 한계

`SET LOCAL enable_indexscan=off`, `enable_bitmapscan=off`, `enable_indexonlyscan=off`는 해당 트랜잭션에서 기존 PK 인덱스 사용까지 제한합니다. 따라서 스캔 제한 측정은 실제로 신규 인덱스만 삭제한 환경과 동일하지 않습니다.

실행 시간은 캐시 및 시스템 부하의 영향을 받습니다. 본 문서에는 반복 측정값을 함께 제시했지만 엄격히 통제된 벤치마크 결과는 아닙니다. 합성 데이터는 고객당 주문이 10건으로 균등하게 배정되어 있으므로 실제 서비스 데이터 분포를 대표하지 않습니다. 제공된 데이터 생성 SQL은 최초 실습에서 사용한 합성 가격 수식을 기준으로 정리했지만, 실행 시점·통계·캐시 등의 차이로 동일한 실행계획이나 실행 시간이 보장되지는 않습니다. 주문상세의 단가는 성능 실습을 위한 합성 값으로, 상품 마스터 가격과 다를 수 있습니다.

## 6. 결론

실행계획에서 불필요한 순차 탐색을 확인하고, WHERE 및 JOIN 조건에 근거해 인덱스를 설계했습니다. 이후 실제 실행계획과 반복 측정으로 접근 방식 및 실행 시간의 변화를 검증했습니다. 본 실습을 통해 통계 정보, 인덱스 설계 및 비교 실험 조건을 함께 고려하는 것이 중요함을 확인했습니다.
